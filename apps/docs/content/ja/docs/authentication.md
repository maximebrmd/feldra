## Better Auth がユーザーの ID を管理します [#better-auth-owns-identity]

どちらのデータベースを選択した場合も、Drizzle アダプターを使用した Better Auth を利用します。Supabase は Postgres としてのみ使用され、Supabase Auth、匿名キー、ブラウザー用データベースクライアントは不要です。

ユーザーはメールアドレスとパスワードで登録し、メールアドレスを確認してからサインインします。アプリケーションにアクセスするには、メールアドレスの確認が必要です。パスワードを忘れた場合のフローとパスワードリセットのフローでは、Resend を通じて有効期限付きのリンクを送信します。

## セッションの保護 [#session-protection]

保護されたレイアウトはナビゲーションを制御しますが、保護されたすべてのルートとページでもサーバー側で認証を行います。所有者 ID は確認済みのセッションから取得し、送信されたフォームデータから取得することはありません。クライアント側の Cookie キャッシュによってセッションの失効が遅れることもありません。

カスタムの更新処理ルートは、リクエストのオリジンを検証します。Better Auth は、独自の CSRF チェックと信頼済みオリジンを管理します。アプリケーションのオリジンは正確に設定し、本番環境では HTTPS を使用してください。

## メールの設定 [#email-configuration]

Resend で送信ドメインを確認し、`RESEND_API_KEY` と `EMAIL_FROM` を設定してください。確認リンクとリセットリンクが正しいホストに戻るように、`APP_URL` をアプリケーションのオリジンに設定してください。

ローカルで生成された認証シークレットは、本番環境で絶対に再利用しないでください。32 文字以上の別の `BETTER_AUTH_SECRET` を設定してください。

## フローの検証 [#verify-the-flow]

```sh
npm run test:database
```

フィクスチャテストスイートは、ローカルの Postgres を使用して、Better Auth の実際の登録、メールアドレス確認、ログイン、リセット、ログアウト、セッション失効を検証します。テスト中はメール送信をインターセプトします。実際の受信トレイへの配信については、別途、ご自身の Resend アカウントで検証する必要があります。

## 代替の Clerk 構成 [#clerk-alternative]

初期化ツールで Clerk を選択するか、`--auth clerk` を指定してください。これにより、Clerk のサインイン、サインアップ、ログアウト、アカウント設定に加え、サーバー側のセッションチェックが生成されます。確認済みのプライマリメールアドレスのみが受け入れられます。ローカルレコードは Clerk のユーザー ID をキーとして管理され、メールアドレスによって自動的に紐付けられることはありません。Stripe のサブスクリプションと非公開メモも、この固定の所有者 ID を維持します。

独立した Clerk アプリケーションを作成し、公開可能キーとシークレットキーを設定してください。認証メールは Clerk が送信するため、この構成では Resend や Better Auth はインストールされません。生成されるガイドには、メールアドレスの確認を必須にする方法、本番環境のオリジンの設定方法、ホストされたフローの検証方法が記載されています。認証情報が不足している場合はアクセスを拒否し、キーなしの Clerk インスタンスを作成することはありません。

上記のセクションは、デフォルトの Better Auth 構成について説明しています。Clerk プロジェクトには、専用の認証設定ガイドとローカルのフィクスチャテストが用意されます。Clerk の実際のログイン、メールアドレス確認、リセット、ログアウトを検証するには、別途、設定済みの開発用インスタンスが必要です。

## 代替の Auth.js 構成 [#authjs-alternative]

初期化ツールで Auth.js を選択するか、`--auth authjs` を指定してください。これにより、GitHub OAuth によるサインイン（同じフローを開始するサインアップページ）、ログアウト、サーバー側のセッションチェックが生成されます。最初の成功したコールバックでローカルユーザーが作成されます。GitHub は確認済みのプライマリメールアドレスを提供する必要があります。ローカルレコードは GitHub のユーザー ID（`github:{id}`）をキーとして管理され、メールアドレスによって自動的に紐付けられることはありません。Stripe のサブスクリプションと非公開メモも、この固定の所有者 ID を維持します。

このプロジェクト用の GitHub OAuth アプリを作成してください。ホームページ URL を `APP_URL` に、認可コールバック URL を `APP_URL/api/auth/callback/github` に設定します。`AUTH_GITHUB_ID` と `AUTH_GITHUB_SECRET` を設定してください。初期化ツールはローカルの `AUTH_SECRET` を書き出します。本番用には別の値を生成してください。Auth.js では Resend や Better Auth はインストールされません。メールアドレスの確認とパスワードの復旧は GitHub が担当します。認証情報が不足している場合はアクセスを拒否し、OAuth アプリをプロビジョニングすることはありません。

Auth.js プロジェクトには、専用の認証設定ガイドとローカルのフィクスチャテストが用意されます。実際の GitHub OAuth を検証するには、設定済みの OAuth アプリが必要です。
