イニシャライザーの各リリースには、テスト済みのモノレポと npm ロックファイルが同梱されています。ひな形の生成時に GitHub からのダウンロードは行われません。`template-origin.json` には、バージョン、プリセット、コンテンツのダイジェストが記録されます。後で比較できるように、生成した各プロジェクトの初期状態を自分でコミットしてください。内部の @repo パッケージはそのプロジェクトに属しており、元のテンプレートからダウンロードされるものではありません。

`packages/config/index.ts`、アプリ内の文言、メタデータ、サンプルのノートをカスタマイズしてください。各プロジェクトは独自のプロバイダーリソースと環境を持ちます。`.env.local` や実際の認証情報は決して配布しないでください。生成されたプロジェクトは create-feldra に依存せず、create-feldra が更新されても自動的に変更されることはありません。

今後の修正では、変更対象のファイル、マイグレーション、検証内容を変更履歴に記載し、イニシャライザーの新しいバージョンを公開してください。旧バージョンと新バージョンから一時的なプロジェクトを生成し、関連する差分を確認して、レビュー済みのパッチを手動で適用してください。カスタマイズとの調整は慎重に行ってください。lint/types/tests/build と、そのプロジェクトの実際のプロバイダーを使用するチェックを実行してください。新しいマイグレーションは順番に適用し、適用済みのマイグレーションは決して書き換えないでください。自動同期やプロバイダーを相互に置き換えるためのレイヤーはありません。

## 既存の 0.1 プロジェクト [#existing-01-projects]

バージョン 0.2 では、ファイルシステムとデプロイモデルが変更されます。このベースを更新しても、0.1 から作成した `my-new-saas` ディレクトリを含め、既存のプロジェクトは変更されません。古いプロジェクトは引き続き使用できます。新しい構造を利用するには、0.2 から**新しい出力先**に生成してください。古いディレクトリに対してイニシャライザーを実行しないでください。

カスタマイズした内容を手動で移行するには、マーケティング用のルートを `apps/web/src/app` に、認証済みユーザー向けのルート、コンポーネント、サンプルのノートを `apps/app/src` に、サービスを対応する `packages` に配置してください。**同じ SaaS** であれば、既存のデータベースとそのマイグレーション履歴を維持してください。このリファクタリングによって SQL スキーマやマイグレーションは変更されません。APP_URL を認証済みユーザー向けアプリのオリジンに、WEB_URL をマーケティングサイトのオリジンに設定してください。Stripe の Webhook とリダイレクトの設定をアプリのオリジンに更新し、メール内のリンクとセッションを再テストしてください。新たに派生させた別の SaaS には、これまでと同様に、独立したプロバイダーリソースを用意する必要があります。

データベース選択機能を導入するリリースでは、Supabase データベースを公開する前にマイグレーション `0001_previous_vampiro.sql` を適用してください。これにより、すべての初期テーブルで、クライアントポリシーを設定せずに RLS が有効になります。既存の Neon プロジェクトにも適用できます。サーバー接続には、テーブル所有者、または明示的に設定した BYPASSRLS ロールを使用する必要があります。元のマイグレーションは保持し、既存のデータベースを作り直さないでください。
