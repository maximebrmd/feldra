## रिलीज़ की स्थिति [#release-status]

Feldra इस परियोजना का नया ब्रांड है। इनिशियलाइज़र पैकेज `feldra` है और इसे अभी npm पर प्रकाशित नहीं किया गया है। स्पष्ट सार्वजनिक रिलीज़ होने तक स्थानीय संस्करण **0.1.0** पर रहता है। प्रकाशन के बाद `npx feldra create` चलाएँ। अनुरक्षक Changesets के माध्यम से संस्करणों का प्रबंधन करते हैं। अप्रकाशित रहते हुए 0.1.0 से आगे बढ़ाने वाले संस्करण PR मर्ज न करें।

## रिलीज़ की कार्यप्रक्रिया [#release-workflow]

```sh
npm run changeset
npm run changeset:status
npm run release:version
```

संस्करण कमांड लंबित टिप्पणियों को संसाधित करता है, `packages/feldra/CHANGELOG.md` बनाता है, इनिशियलाइज़र और रूट के संस्करणों को अपडेट करता है, और लॉकफ़ाइल को अद्यतन करता है। यह प्रकाशित नहीं करता है। 0.1.0 को npm के लिए अधिकृत किए जाने तक लंबित changesets को खपत न करें। स्पष्ट रूप से अधिकृत npm प्रकाशन से पहले पैक किए गए आर्टिफ़ैक्ट का परीक्षण करें। देखें [रिपॉज़िटरी की रिलीज़ मार्गदर्शिका](https://github.com/maximebrmd/feldra/blob/main/docs/releasing.md)।

## स्थानीय रिलीज़ का इतिहास [#local-release-history]

### 0.1.0 — पहली सार्वजनिक रिलीज़ (अभी प्रकाशित नहीं) [#010-\-first-public-release-not-published-yet]

ट्री में पहले 0.2.0/0.3.0 के रूप में क्रमांकित स्थानीय विकास इतिहास, जो npm पर कभी प्रकाशित नहीं हुआ, साथ ही लंबित changeset नोट्स:

- **Breaking:** प्रकाशित पैकेज और CLI का नाम `create-feldra` से `feldra` करें। `npm create feldra` के बजाय `npx feldra create` चलाएँ। बिना आर्ग्युमेंट वाला `npx feldra` `create` सूचीबद्ध करते हुए सहायता दिखाता है।
- टेम्पलेट का नाम Feldra करें। जनरेट किए गए प्रोजेक्ट्स की ब्रांडिंग, CLI कमांड, रिलीज़ मेटाडेटा, परीक्षण और दस्तावेज़ीकरण अपडेट करें। npm प्रकाशन एक अलग रिलीज़ चरण ही रहता है।
- इनिशियलाइज़र पैकेज को `initializer/` से `packages/feldra` में ले जाएँ।
- Changesets और जनरेट किए गए चेंजलॉग से इनिशियलाइज़र रिलीज़ प्रबंधित करें। रिलीज़ टूलिंग को जनरेट किए गए SaaS प्रोजेक्ट्स के बाहर रखें और रिलीज़ संस्करणों को बंडल किए गए टेम्पलेट के साथ सिंक करें।
- स्रोत-रिपॉज़िटरी README के बजाय जनरेट किए गए प्रोजेक्ट्स में उत्पाद README शामिल करें।
- स्वतंत्र Feldra Astro दस्तावेज़ीकरण साइट जोड़ें और उसके ऐप तथा टूलिंग को जनरेट किए गए SaaS प्रोजेक्ट्स से बाहर रखें। Astro जाँच के अनुकूल साझा TypeScript संस्करण का उपयोग करें।
- Neon या Supabase के साथ स्वतंत्र Better Auth या Clerk चयन जोड़ें। Clerk कोड और हल की गई डिपेंडेंसी लॉकफ़ाइल बंडल करें, Clerk प्रोजेक्ट्स से अप्रयुक्त Better Auth/Resend टूलिंग हटाएँ, सर्वर प्राधिकरण बनाए रखें, और प्रबंधित प्रमाणीकरण सेटअप तथा लाइव सत्यापन की सीमाएँ दस्तावेज़ित करें।
- तीर कुंजियों से इंटरैक्टिव Neon/Supabase डेटाबेस चयन, साथ ही CI के लिए `--database`।
- प्रदाता के अनुसार जनरेट किए गए सेटअप निर्देश, परिवेश संबंधी टिप्पणियाँ और स्रोत का मेटाडेटा।
- सभी निजी तालिकाओं पर RLS सक्षम करें; सर्वर पर स्वामित्व की जाँच और साझा Postgres/Drizzle पहुँच बनाए रखें।
- पैक की गई npm रिलीज़ से दोनों डेटाबेस विकल्पों का परीक्षण करें।
- अलग-अलग मार्केटिंग और प्रमाणीकरण वाले Next ऐप्स, स्रोत कोड निर्यात करने वाले छह साझा पैकेजों और Turborepo के साथ next-forge शैली का npm मोनोरेपो जनरेट करें।
- टर्मिनल में सेटअप/समीक्षा प्रॉम्प्ट और `--preset neon` जोड़ें, तथा `--yes`/गैर-TTY स्वचालन बनाए रखें। ऐसे प्रदाताओं के विकल्प शामिल न करें जिन्हें लागू नहीं किया गया है।
- लागू किए गए Neon/Better Auth/Stripe/Resend टूलकिट और अपरिवर्तित डेटाबेस माइग्रेशन को बनाए रखें।
- दोनों प्रोडक्शन ऐप्स, ऐप्स के बीच नेविगेशन, वर्कस्पेस टास्क ग्राफ़ और वास्तविक पैक किए गए वितरण का परीक्षण करें। पहले से जनरेट की गई परियोजनाएँ अपने-आप संशोधित नहीं होती हैं।
- प्रारंभिक एकल-ऐप SaaS आधार और साथ में शामिल npm इनिशियलाइज़र, जिसे बाद में ऊपर दी गई मोनोरेपो आर्किटेक्चर ने प्रतिस्थापित किया।
