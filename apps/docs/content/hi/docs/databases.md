इनिशियलाइज़र में आप ऐरो कुंजियों और Enter का उपयोग करके Neon और Supabase में से चुन सकते हैं। गैर-इंटरैक्टिव कमांड में `--yes --database neon` या `--yes --database supabase` का उपयोग करें। Neon डिफ़ॉल्ट विकल्प है। चुना गया डेटाबेस `template-origin.json`, `.env.example` और `DATABASE.md` में दर्ज किया जाता है।

दोनों विकल्प एक ही Drizzle स्कीमा, माइग्रेशन, node-postgres ड्राइवर और Better Auth Drizzle अडैप्टर का उपयोग करते हैं। ये मानक Postgres कनेक्शन हैं; किसी Supabase SDK, Supabase Auth, अनाम कुंजी या service-role API कुंजी की आवश्यकता नहीं है। डेटाबेस का चयन सेटअप निर्देशों को बदलता है, आपके एप्लिकेशन API को नहीं। इनिशियलाइज़र कोई संसाधन प्रावधान नहीं करता है।

## Neon

प्रत्येक SaaS के लिए एक स्वतंत्र Neon प्रोजेक्ट बनाएँ। पूल किए गए कनेक्शन URL को `DATABASE_URL` में और डायरेक्ट URL को `DATABASE_URL_UNPOOLED` में कॉपी करें। Neon द्वारा दिए गए कनेक्शन सुरक्षा पैरामीटर बनाए रखें। डेवलपमेंट और प्रोडक्शन के लिए अलग-अलग ब्रांच/डेटाबेस कॉन्फ़िगर करें।

## Supabase

प्रत्येक SaaS के लिए एक स्वतंत्र Supabase प्रोजेक्ट बनाएँ। डैशबोर्ड के **कनेक्ट** पैनल में **ट्रांज़ैक्शन पूलर** की कनेक्शन स्ट्रिंग (पोर्ट 6543) को `DATABASE_URL` में कॉपी करें। `DATABASE_URL_UNPOOLED` (माइग्रेशन) के लिए **डायरेक्ट कनेक्शन** का उपयोग करें; केवल IPv4 वाले नेटवर्क पर इसके बजाय **सेशन पूलर** (पोर्ट 5432) का उपयोग करें। डैशबोर्ड से होस्ट और उपयोगकर्ता नाम हूबहू कॉपी करें, URL एन्कोडिंग के साथ अपना डेटाबेस पासवर्ड डालें और आवश्यक TLS सेटिंग बनाए रखें। कनेक्शन त्रुटियों से बचने के लिए प्रमाणपत्र सत्यापन अक्षम न करें। [Supabase कनेक्शन विकल्प](https://supabase.com/docs/guides/database/connecting-to-postgres) देखें।

सर्वर और माइग्रेशन के लिए प्रोजेक्ट द्वारा दिए गए डेटाबेस स्वामी के क्रेडेंशियल का उपयोग करें। ट्रांज़ैक्शन पूलर नामित प्रिपेयर्ड स्टेटमेंट का समर्थन नहीं करता है; यह टेम्पलेट ऐसा कोई स्टेटमेंट नहीं बनाता है। कनेक्शन मोड की दोबारा समीक्षा किए बिना `.prepare()` क्वेरी न जोड़ें। सर्वर पूल प्रत्येक प्रक्रिया के लिए एक कनेक्शन का उपयोग करता है; डिप्लॉयमेंट में समवर्ती प्रक्रियाओं की संख्या फिर भी आपके प्रदाता की कनेक्शन सीमाओं के अनुरूप होनी चाहिए।

Supabase प्रोजेक्ट सेटिंग में अप्रयुक्त **डेटा API** अक्षम करें। यह टेम्पलेट केवल प्रमाणीकरणयुक्त Next.js रूट हैंडलर के माध्यम से डेटा उपलब्ध कराता है। इसका माइग्रेशन क्लाइंट नीतियों के बिना सभी नौ तालिकाओं पर पंक्ति-स्तरीय सुरक्षा सक्षम करता है। इससे ऐसी भूमिकाओं के लिए पढ़ना और लिखना प्रतिबंधित हो जाता है जो स्वामी नहीं हैं और जिनके पास BYPASSRLS नहीं है, भले ही तालिका संबंधी अनुमतियाँ मौजूद हों। यह ऑथ टोकन, पासवर्ड हैश, बिलिंग स्थिति और निजी नोट्स को सीधे क्लाइंट एक्सेस से सुरक्षित रखता है। सर्वर क्वेरी तालिका के स्वामी के रूप में चलती हैं, जो RLS को बायपास करता है; सर्वर पर उपयोगकर्ता स्वामित्व की जाँच अनिवार्य बनी रहती है। Supabase service-role API एक्सेस भी RLS को बायपास करता है; उस कुंजी को निजी रखें। डेटाबेस URL कभी भी ब्राउज़र में उजागर न करें। [Supabase API सुरक्षा](https://supabase.com/docs/guides/api/securing-your-api) और [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) देखें।

आप जो भी नई तालिकाएँ जोड़ें, उन पर RLS सक्षम रखें। यदि आप बाद में डेटा API सक्षम करते हैं, तो उपलब्ध कराए गए स्कीमा, तालिका संबंधी अनुमतियों और नीतियों की स्पष्ट रूप से समीक्षा करें; Better Auth सेशन, Supabase JWT नहीं हैं। Supabase Auth का कोई एकीकरण शामिल नहीं है।

## सेटअप पूरा करें [#finish-setup]

[सेटअप](/docs/environment/) में बताए अनुसार Resend और Stripe के मान भरें, फिर जनरेट किए गए प्रोजेक्ट की रूट डायरेक्टरी से चलाएँ:

```sh
npm run db:migrate
npm run check
npm run dev
```

`.env.local` को निजी रखें। प्रत्येक प्रोजेक्ट और परिवेश के लिए अलग-अलग क्रेडेंशियल और प्रदाता संसाधनों का उपयोग करें। किसी नए डेटाबेस पर ट्रैफ़िक की अनुमति देने से पहले माइग्रेशन चलाना अनिवार्य है। टेस्ट फ़िक्स्चर अस्थायी स्थानीय Postgres का उपयोग करते हैं; लाइव Neon/Supabase कनेक्टिविटी के लिए आपके क्रेडेंशियल आवश्यक हैं और फ़िक्स्चर परीक्षणों द्वारा इसका सत्यापन नहीं किया जाता है।
