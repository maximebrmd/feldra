# Supabase Auth

This project was generated with Supabase Auth rather than Better Auth. Create a separate Supabase project for authentication. Enable email/password, turn on **Confirm email**, and add this application's origin plus `http://localhost:3001/api/auth/callback` (production: `https://app.your-domain.com/api/auth/callback`) to Auth redirect URLs. Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `.env.local` and production hosting. The legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` still works if a publishable key is unset. Rebuild after changing public keys. Never add the service role key. No Supabase account or project is created automatically.

Supabase Auth is independent of `--database`. You can keep Neon (or another Postgres) for application data and still use a Supabase project for identity. When both choices are Supabase, use the same project if you want; the app still talks to Postgres through Drizzle/`pg`, not the Data API.

Email/password forms handle signup, login, verification resend, password reset and logout. Supabase sends authentication emails; this variant does not install Resend or Better Auth. Set the Auth password minimum to 12 characters so it matches the form. `/dashboard/settings` keeps the local display name; password changes go through the reset flow after the emailed link.

Every protected page and API handler resolves the signed-in Supabase user on the server. The Next.js proxy refreshes the session cookie and is **not** the authorization gate. Handlers call `getClaims()` for a validated session id and `getUser()` for a fresh provider record, then require a confirmed email. The local user is synchronized by Supabase user ID, never by email. Conflicting email addresses fail closed rather than linking accounts. A provider outage fails closed. The fresh provider read avoids granting access from stale email claims. Account deletion in Supabase Auth revokes access; local notes and billing records remain until an explicit retention/deletion process handles them. Existing Stripe subscriptions are not silently canceled by deleting an identity.

Both database options keep the same Postgres schema and migration history. Better Auth's session/account/verification/rate-limit tables are dormant in this variant; no Supabase session or password is stored in them. Keep them when applying shared database fixes; remove them with an explicit migration if desired. This initializer creates new projects; changing a flag is not an existing-user migration between providers.

`npm run check` runs types, unit tests and builds without credentials. `npm run test:database` uses local Postgres fixtures for verified identity mapping, repeat synchronization, email collision refusal, ownership, invalid input and RLS. The SDK login, verification, reset and logout flows still need testing against your configured Supabase Auth project. The Better Auth browser fixture is omitted because it cannot exercise Supabase's hosted identity service. Stripe policy tests remain; use a Stripe sandbox to verify Checkout and webhook delivery. No mock identity bypass ships in application code.
